# 实机连接与传输留证

目前 CI 只证明同一主机上的浏览器直连与文件协议，不能替代公网 NAT 测试。本说明用于下一阶段的真实设备验收；下列步骤本身不代表测试已执行。

## 开始前

- 使用同一开发提交构建，在自己控制的 HTTPS 站点部署，精确配置 WSS Origin；不得开放文件上传或 TURN。域名和服务器需已实际具备，`zeydrop.com` 未确认拥有。
- 每组记录提交 SHA、两个设备/OS/浏览器版本、网络类型与运营商、是否启用 IPv6/VPN/企业策略。不需要公开真实 IP、邀请链接、恢复令牌或文件内容。
- 先完成同 Wi-Fi，再按 TEST_MATRIX 逐组执行不同宽带、宽带与蜂窝、不同移动运营商、IPv6/双栈、严格 NAT。不能连上的组合保留失败结论。

## 每组操作

1. 创建邀请，第二台加入；核对两端安全码。只有 UI 显示已核验 selected 直连路径才能记录连接成功。信令在线、出现候选或显示邀请均不算成功。
2. 在两端点击“导出连接诊断”，失败时也导出。JSON 只在本机下载，包含版本/revision、匿名 peer 序号、最多 120 条状态、候选类型/数量、路径协议/地址族/RTT。先检查内容再主动分享；不需要发送完整 getStats/SDP。
3. 发送已知文本、随机二进制、图片/视频、多文件，接收方先拒绝一次再同意。接收前不能收到正文；完成后在发送/接收设备独立计算 SHA-256 比较，不能仅看 UI 的完成提示。
4. 执行 100 MB 和 1 GiB。真实保存 picker 应由接收点击触发，验证取消授权、磁盘空间不足、写入失败。无流式能力超过合计 64 MiB 应在传输前拒绝；不能为了过测放大内存池。
5. 验证暂停/继续、发送与接收端取消、拒绝后再发送、队列保存/丢弃后进入下一项。中断网络/切换网络/冻结后台后：同一页面原设备短时恢复可尝试在 **120 秒**内重新核对安全码和前缀 SHA-256 续传；接收方**主动选择** OPFS 暂存时，跨刷新后须用**新邀请**重新配对，发送端重新选择原文件且双方校验已保存前缀。不能从 UI 显示恢复状态就推断真实已续传；记录最终 SHA-256、实际补传字节数和失败情况。无能力/权限的浏览器应明确拒绝持久化。
6. 记录页面资源、信令、STUN 与文件正文流量的区别。只用网络抓包或服务器侧观测证明是否有正文；诊断 JSON 不提供服务器流量证明。不得向证据中写入私密文件内容。
7. 各平台 PWA 安装、旧版本打开时部署新版、传输期间不强刷、关闭所有旧标签后重新打开，确认 revision 更新。
8. 新发送任务流程：拒绝第一项后检查后续队列保留且不自动弹新请求；手动重新发送必须再次取得接收同意。后续队列可继续/清空，原Blob待保存时不能绕过屏障；断线/15分钟后旧失败重试引用应失效。
9. 主动勾选本机发送清单并选多文件，刷新后确认没有自动发送或绑定原件；建立新配对/核码、重选全部原件（可反序），同名同尺寸异内容必须拒绝。最终完整成功后才逐项移除，失败/取消保留。检查撤回存储同意、停止哈希、另一标签修改、清站点数据/存储驱逐/额度不足均不能误发文件；无能力时仍能普通发送。


## 离线核验两端证据（不上传）

双方完成测试后，可将**自己掌控的**两个脱敏诊断 JSON 以及原始/接收文件放到同一台用于核验的电脑上，使用 Node.js 22+。本工具**不访问网络，不上传、转发或保存文件正文**，并且不会在报告中写出文件名、系统路径、IP、邀请、令牌或原始 SHA-256 摘要。

```bash
node scripts/field-verify.cjs --sender-diag sender.json --receiver-diag receiver.json \
  --sender-file original.bin --receiver-file downloaded.bin \
  --scenario broadband-cellular --out local-field-report.json
```

可以省略两个 `--*-file` 参数只核验连接诊断，但此时结论会是 `direct-route-diagnostic-only`，**不能视作完成文件传输验收**。仅支持 `same-wifi`、`different-broadband`、`broadband-cellular`、`different-carriers`、`ipv6-dual-stack`、`strict-nat`、`network-switch`、`unknown` 这些预设场景，避免把可识别网络描述写入报告。

结论分别为：`evidence-consistent`（两份客户端诊断都记录当前非 relay selected route / 相同版本、两端文件本地 SHA-256 一致）；`direct-route-diagnostic-only`（没有提供文件）；`integrity-mismatch`（文件内容不一致）；`not-confirmed`（路径或版本信息不足）。报告只是**本地一致性检查**，诊断均来自客户端而非独立路径证明；场景名称由测试人员填写，也不能证明运营商/NAT 拓扑。还需测试人员记录真机设备/网络条件、实际抓包/服务器流量，才可形成公网实测证据；不能据此推算普遍 NAT 成功率。无文件摘要会写入输出报告，结果文件应由测试人员审阅后再公开。

## 2026-11-07 新增实机数据保留与PWA步骤

1. 使用测试文件副本和独立浏览器配置建立自愿OPFS断点；记录已提交offset/SHA。准备读取时取消/切网，以及继续write/checkpoint/finish期间权限或配额失败后，检查此前已提交记录仍可重新选择、重新授权及全前缀校验。未提交尾部允许截断，不按进度百分比认定持久化。
2. 在接近最终保存时切网/后台冻结，检查本机已验证记录可管理/独立哈希；对端不得因迟到结果自动显示完成。另测试超过120秒后再恢复，不能auto-adopt过期状态或把新offset配旧SHA。
3. 区分保留操作和主动取消：当前文件的主动取消/手动删除会执行相应删除策略，准备阶段取消保留旧checkpoint；需要继续的任务先验证暂停/重新恢复。确证内容损坏不能被当正常断点续传。
4. 实测浏览器驱逐、磁盘耗尽/权限、native close失败/卡住、进程崩溃和多标签锁。源代码夹具已验证清理策略，但逻辑取消不保证底层立即解锁；不要把RPC/磁盘挂起标成成功。
5. 用真实OS断网、新文档缓存加载与原生Worker核查PWA；再测试新版本等待旧标签关闭、离线/在线切换、旧缓存被驱逐及移动后台。CI只仿真请求阻断和renderer网络提示，没有物理断网或完成PWA升级生命周期验收。

核对源码候选精确commit/revision/manifest和自己的独立文件SHA；最终云端证据见TEST_REPORT_20261107_FINAL，Issues #4/#5仍open。
