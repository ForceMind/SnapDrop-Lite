# 服务端真实墙钟 soak

`scripts/server-soak.cjs` 在当前测试主机 fork **一个新的回环信令服务**，不连接已有服务、远程 URL、用户服务器或用户电脑。它使用实际 WebSocket、配对和恢复令牌，但只产生固定格式的合成 SDP 控制消息；不创建 WebRTC、ICE、DataChannel，也不读取或发送用户文件。结果不是公网 P2P、NAT 成功率、文件吞吐或生产容量证据。

## 启动与时限

先安装仓库锁定依赖，再运行：

```bash
node scripts/server-soak.cjs --help
node scripts/server-soak.cjs --duration-seconds 3600 --connections 64 --out test-results/server-soak-1h.json
```

| 参数 | 默认 | 范围与行为 |
|---|---:|---|
| `--duration-seconds` | 3600 | 1–3600 整数；从全部连接配对完成后计算实际活动时间 |
| `--connections` | 64 | 2–1000 的偶数；每两端形成一个锁定房间 |
| `--out` | 不写文件 | 主动指定本机 JSON 路径；报告本身不导出路径 |

命令实际总时长比活动窗口长：启动/配对后执行活动窗口，关闭全部 WS，**真实等待至少 120 秒恢复 grace，再等待服务端原有 5 秒定时 sweep**。父进程和子进程的硬截止均为 `durationSeconds × 1000 + 120000 + 90000` 毫秒（最长 3810 秒）：120 秒是真实保留期限，另外 90 秒覆盖启动、关闭及自动清理余量。超时报告失败并终止隔离子进程，不延长到后台自动任务。

工具没有时钟注入，不修改 `Date.now()`，不手动调用 `sweep()`，不缩短服务端 TTL。活动时间与期限使用真实计时；报告包含 UTC 开始时间及单调墙钟耗时。会话原本最长 12 小时，此工具最多观察一小时，不等于完整 12 小时或多日稳定性验收。

运行中，`--out` 文件以原子替换方式保持有效 JSON，`status=running` 明确表示尚未完成。stderr 仅输出固定字段的进度 JSON 行；stdout 在结束后输出完整报告。只有活动阶段成功、原身份恢复成功、信令精确收齐、真实 grace 后资源归零才会写入 `status=passed`。提前结束或仍在运行的文件不得记作通过。

## 负载与计量

- 默认 64 条连接 / 64 个 session / 32 个配对房。每端每 15 秒发送一条小型合成 SDP；收到服务端真实 `ping` 时回复 `pong`。消息序列逐一匹配实际转发的发送者/接收者，核对已发送消息是否精确收齐，并在活动循环中检查关闭/异常标记；最后一个窗口的检查边界见下文。
- 每 60 秒轮转断开约 1/8 的连接，等待服务端实际 detach，再用原令牌重新连接。核对 peer ID、恢复令牌、原锁定房间及总资源计数保持一致；报告只输出成功次数，不输出任何身份/房间/令牌。
- 每分钟保存服务端子进程 RSS、heap、external、OS RSS 高水位、累计 CPU、窗口 CPU 差额、连接/session/房间/WS client 数及合成信令延迟。启动、结束和 grace 阶段另有快照，最多 70 个；保留期限中间也采一次快照。父进程负载发生器不计入这些服务端 RSS/CPU。
- 子进程以 96 MiB V8 old-space 上限启动；**没有施加 OS/cgroup/systemd MemoryMax**，不把 V8 上限当作 RSS 上限。`maxSocketBufferedBytesAtSample` 只是采样时值，非完整运行的缓冲峰值。RSS 不要求回到零或启动基线。
- 服务端每条实际入站控制消息处理后观察其原有分钟消息/字节计数，保存观测到的最大值，要求不超过 240 条、512 KiB 预算。低频 SDP、心跳和恢复 hello 都包含在计数中；这是正常负载遵守预算的观察，不替代独立恶意限流测试。
- 延迟使用固定分桶直方图累计，报告均值、最大值和 p50/p95 的**桶上界**，不保存全部消息样本。待收信令最多一轮 / 每连接一条；客户端控制收件箱最多 16 条；没有随小时无限增长的逐消息数组。
- 关闭所有 WS 后，先核对连接归零、session/配对房仍被保留；60 秒再次核对保留状态；至少 120 秒后等待原生 sweep 将连接、session、房间及 WS client 全部清零。进程自身和分配器保留 RSS 不是泄漏证明，需结合更长/重复曲线另行研究。

JSON 只导出固定状态、计数、耗时、资源数字、Node/平台/架构以及 server/tool 源码 SHA-256。peer/room ID、恢复令牌、SDP、IP、完整错误、用户文件名和输出系统路径都不进入报告。工具不上传报告，也不提供远程目标参数。

## 初版长测工具的监测边界与修复

本次运行的工具 SHA-256 为 `b19fd3b4e5793a415c5f680af56c307e0967675a08c944ec6b151725aa10633b`。活动循环只在每轮开头检查客户端关闭及 `client.failure` 标记，退出活动循环后再核对服务端资源及信令收发总数，没有额外重查该客户端异常标记。因此，最后一次 sleep 窗口内出现的额外重复 / 未知控制消息，即使被 handler 标记为异常，若未改变预期收发总数和资源计数，也可能未使最终状态失败。

这是监测覆盖边界，尚未观察到该异常由产品服务实际触发。正在运行的一小时结果只能用于其精确源码下的正常预期信令、原身份恢复、资源采样及真实 grace 回收，不能表述为“所有末尾异常都被捕获”。此边界已在后续工具中修复：活动结束后及写入最终成功状态前重查客户端异常；真实WS末尾错误回归先红后绿。初版保存在提交4d617b1，运行中的长测仍使用初版源码哈希，不能冒充后续工具的完整小时验收。
