# 闪投：公网 P2P 直连（Direct-only）开发计划

> 状态：开发方案（尚未实施功能改造）  
> 审计日期：2026-10-19  
> 仓库：`ForceMind/SnapDrop-Lite`  
> 审计基线：`main@09d2edc51463cb92a2627cf71681cfc5abced432`  
> 目标：在保留现有局域网文件传输体验的基础上，实现跨运营商/跨地域的公网 P2P 传输，服务器只负责网页静态资源、设备配对和信令，不承载文件正文。

## 0. 不可妥协的产品边界

1. **文件永远不经自有服务器转发或存储。** 服务器不提供文件上传、下载或 TURN 中继；不能通过 WebSocket 偷偷兜底为文件中转。
2. **直连失败就明确失败。** 不以牺牲服务器文件带宽换成功率，不虚构“所有网络都可以 P2P”。
3. **信令流量不等于零流量。** WebSocket/HTTPS 配对、心跳和 ICE 候选必然产生少量服务器流量；STUN 也是少量探测流量，但不承载文件正文。使用第三方 STUN 时仍须评估可用性与隐私。
4. **保留 Web/PWA。** 优先复用当前 HTML/CSS/JS + Node.js + WebRTC DataChannel 架构，避免为了公网穿透而整体重写。
5. **局域网功能不能倒退。** 局域网快速发现和文本/文件传输继续保留，但公网使用显式配对，不能把相同公网 IP、CGNAT 或相同 IPv6 /64 一概视为可信的同一局域网。
6. **权限与信任清晰。** 接收文件前须由接收方明确接受；配对会话短期有效，避免通过可猜测的公共房间号探测陌生设备。
7. 不创建定时任务；按版本分阶段实施和验证，完成一阶段再进入下一阶段。

## 2. 目标架构与数据边界

```text
浏览器/设备 A                    闪投服务器                   浏览器/设备 B
    |---- HTTPS/WSS 配对 --------->|<--------- HTTPS/WSS 配对 ----|
    |<-- 房间状态/批准/SDP/ICE --->|<---- 房间状态/SDP/ICE ----->|
    |                              |
    |<============== WebRTC DataChannel / P2P ================>|
    |                    文件字节不经过服务器                  |
```

- 服务端仅允许：`hello`、`pair-create`、`pair-join`、`pair-accept`、`offer`、`answer`、`ice`、`leave`、`ping/pong` 等结构化信令。消息格式定义严格 schema，限制长度与速率。
- WebRTC `iceServers` **只配置 STUN，没有 TURN**。明确 `iceTransportPolicy: "all"` 本身不是“只允许直连”的开关；“无 TURN 凭据和无中继路径”才是核心约束。
- 使用 `getStats()` 或可用的 ICE transport API 读取**实际选中的** candidate pair：`relay` 一律阻止文件传输；`host/srflx/prflx` 可视为非 TURN 路径，仍需报告 IP 族、连接状况和是否成功。
- IPv4/IPv6 并行候选与连通性检测；优先使用标准 ICE，不私自实现不兼容的 UDP NAT 穿透算法。
- 服务端**不能靠客户端协议自觉**限制中转：WebSocket 服务本身应拒绝二进制消息、未列入白名单的数据结构、超大信令、超频候选及未授权目标转发。
- 房间采用一次性高熵邀请凭证（推荐至少 128 bit，二维码/链接传送），短码仅作为查找码且配合严格限流、有效期及发送方批准；协议要考虑恶意信令服务器或中间人替换身份的问题，后续可加入双方校验码。
- 不把相同公网 IP 或 IPv6 前缀自动解释为可信设备归属。公网默认显式配对；局域网自动发现保留但单独处理。

## 3. 开发里程碑及验收条件

### M0 — 冻结基线、统一产品事实（先做）

- 从当前 `main` 创建功能分支，记录已有功能、协议、构建步骤与最小冒烟测试。
- 调整 README：明确现状、非中继目标、直连失败限制，移除错误的“自动 WebSocket 中转”表述。
- 增加测试骨架（Node 内置测试或轻量测试框架）及 CI：源码语法检查、依赖安装、静态协议单测、构建产物一致性。
- 清理错误/误导性日志；区分“已连接信令服务器”和“已经建立文件 P2P 连接”。

**完成标准：** 从干净检出可重复构建；基线测试自动执行；文档说明与源码一致；不改变当前已工作的 LAN 文件发送路径。

### M1 — 公网发现、信令配对、只直连安全边界（核心可用版）

- 修复 `deploy.sh` 中的 STUN 开关，改为明确的 `P2P_MODE=lan|public-direct` 配置（可以保留兼容旧变量的迁移层）。
- `public-direct` 启用经验证的 STUN 列表与超时策略；服务端**不得启用 TURN**。开发环境与生产环境区分配置，不硬编码一大堆未经验证的第三方 STUN 域名。
- 新建房间/配对协议及 UI：创建一次性房间 -> 分享码或二维码 -> 对方加入 -> 发送方同意 -> ICE 协商。
- `join-room` 改为排队到 WS open 后发送，接收服务端加入成功/失败确认；网络重连自动重新鉴权/重新入房，更新 UI 真实状态。
- 处理同浏览器多标签 peer ID 冲突，使用安全随机会话标识；服务端正确监听 socket close 并清除房间状态。
- 收紧 WebSocket：消息 schema、`maxPayload`（按实测 SDP 上限设置，例如初值 64 KiB）、拒绝非信令 payload、限流、会话绑定、Origin 检查与可信代理 IP 配置。
- 接收前展示发送设备、文件名与大小并获得确认；不能在未接受前自动持续接收全部文件。
- 部署模板提供 HTTPS/WSS 示例，WebSocket 只监听 loopback 或受保护端口。

**完成标准：** 不同公网 IP 的两端能通过一次性配对进入同一信令会话；在可穿透网络中建立真正的 DataChannel 直连；禁用 TURN 且关闭信令服务器文件正文通路；拒绝未经批准的传输。

### M2 — ICE 连接稳定性与路径可观测

- 将连接生命周期整理为显式状态机：`idle -> pairing -> signaling -> gathering -> checking -> direct-connected | failed | closed`。
- 补齐候选排队、双方同时发起协商的正确处理（参考 Perfect Negotiation 模式）、受限次数的 ICE restart、网络切换检测、退避与取消逻辑。
- 通过 `getStats()` 输出最终选中 ICE candidate pair、候选类型、IPv4/IPv6、RTT（如可用）、传输字节数；不采集用户文件内容。
- UI 区分：“等待对方”“打洞中”“UDP 直连”“无法直连”“设备离线”；显示可理解的失败原因和是否可尝试其他网络。
- 强制 Direct-only 验证：没有选中的候选或发现 `relay` 时不得进入文件传输状态。

**完成标准：** 断网、Wi-Fi 与移动网络切换、浏览器恢复、对端离线/拒绝等场景能正确收敛到成功或可重试失败，不出现无限重连或虚假直连提示。

### M3 — 大文件与断点续传

- 定义版本化文件协议：`file-offer/accept/chunk/ack/pause/resume/cancel/complete/error`，包含 `transferId`、文件大小、分块序号与偏移。
- 发送端按浏览器协商能力选择分块大小，使用 `bufferedAmount` + `bufferedamountlow` 限制排队，避免无背压无限 `send`。
- 接收端使用可用的流式写入方式（支持时使用 File System Access API）。不支持的浏览器采用受控的内存/Blob 路径并清楚提示文件大小限制；尤其针对 Safari/iOS 制定兼容策略。
- 加入分段/文件 SHA-256 校验、缺块处理、重试、暂停和恢复（恢复只适用于两端重新建立直连且拥有相同文件/临时数据的情况）。
- 修复零字节文件、`repeatPartition` 死路径、接收拒绝、文件名校验、下载中断和 UI 完成态判定。
- 保留文本传输、图片拖拽/粘贴和多文件队列，避免旧功能倒退。

**完成标准：** 正常文件比对校验值一致；支持多文件、断点、网络抖动与取消；支持的浏览器实测 1 GiB 文件不因“完整文件常驻 JS 数组”而崩溃；受限浏览器按能力限制并明示，而非承诺全部支持。

### M4 — 安全、部署、兼容性与发布

- 升级维护中的 Node.js 版本及直接依赖，重新生成 lockfile 并运行依赖安全审计；变更范围以实际兼容性与报告为准。
- 更新 Nginx TLS/WSS、反向代理可信头、请求体/WS 负载上限、健康检查、结构化无敏感信息日志与配置检查。
- 修复 Service Worker 版本缓存、旧客户端与新信令协议兼容性；增加部署回滚方案、配置迁移说明。
- 自动化测试覆盖信令授权、房间到期、消息上限、路径拒绝、协议状态机、传输完整性和构建；实机验证 Chrome/Edge、Firefox、Safari、Android Chrome/iOS Safari。
- 生产发布前核对：公网只开放必要的 HTTPS/WSS 服务，服务器没有 TURN/上传路径；执行服务端出站流量审计并留存测试记录。

**完成标准：** 发布版本可回滚，CI 与目标跨设备矩阵通过；经过 100 MiB 和 1 GiB 直连传输时，服务器出站数据只产生心跳/信令/HTTP 资源等少量开销，不随文件大小线性增长。

### M5 — 可选原生增强（非 Web MVP 的前置条件）

- 若未来提供 Windows/macOS/Android 原生客户端，可评估 PCP/NAT-PMP/UPnP 端口映射、IPv6 入站策略与更精细的网络诊断，以增加可直连网络比例。
- 不把浏览器无法控制的路由器端口映射能力当作 Web 版必备功能。
- 任何原生增强都继续遵守“文件不经自有服务器”的底线。

## 4. 具体测试矩阵

| 场景 | 预期 |
| --- | --- |
| 同一 Wi-Fi 两端浏览器 | 仍能发现/配对、直接传文件 |
| 家庭宽带 A ↔ 另一家庭宽带 B | 可配对；可打洞则 `direct-connected`，不能时明确失败 |
| 家庭 Wi-Fi ↔ 4G/5G | 同上，并记录 ICE 候选类型 |
| 不同运营商移动网络 ↔ 移动网络 | 不保证穿透，必须有确定的失败反馈 |
| 双栈 IPv4/IPv6 网络 | 尝试可用的 v4/v6 非中继连接，显示实际路径 |
| 严格 NAT/企业防火墙 | 不启用 TURN；失败提示而非服务器中转 |
| WebSocket 在协商过程中断开 | 可重连并恢复房间或要求重新授权 |
| 传输中断线/切网络/浏览器刷新 | 不误报完成；在能力允许下恢复已确认分块 |
| 空文件/中文文件名/大量小文件/1 GiB 大文件 | 内容校验、一致性与受控内存行为 |
| 恶意 WS 大包、任意 `to`、未批准加入、暴力猜码 | 服务端拒绝，不允许当文件代理使用 |

执行每个跨网络案例时记录：两端浏览器/系统、网络类型、ICE 候选类型、选中 pair、握手是否成功、握手耗时、吞吐、文件校验结果及脱敏的信令字节数；先测得真实基线，再设成功率目标，不虚构保证值。

## 5. 实施顺序与版本门槛

1. **第一交付：M0 + M1，公网直连最小闭环。** 先修 STUN、配对与信令权限，拿到“异地能配对且直连时文件不走服务器”的最小可用版本。
2. **第二交付：M2，真实可观测和可恢复的连接。** 用统计数据核验连接类型；明确失败原因，排除 UI 假阳性。
3. **第三交付：M3，大文件可用版。** 端到端完整性、背压与受限浏览器的内存安全。
4. **第四交付：M4，安全与正式发布。** 配套 CI、依赖、部署、测试矩阵、回滚。
5. **可选后续：M5，原生直连增强。**

每个阶段独立 PR/提交和验证，不合并未经验证的公网“可用”声明。

## 6. 尚未完成与风险说明

- **尚未进行任何实机公网打洞测试。** 当前文档只记录 GitHub 仓库的静态代码审计以及目标设计。
- **公网直连不可能做到 100% 成功。** 对称型 NAT、CGNAT、防火墙及部分运营商限制可能让非中继路径不可用。
- **不能将“服务器文件流量 0”误写成“总网络流量 0”。** 网站加载、信令与自建 STUN 探测仍有少量消耗；可审计的是文件正文不进入服务器。
- **浏览器大文件持久化能力不一致。** File System Access API 在部分浏览器不可用，不能承诺跨全部浏览器的无上限文件传输。
- **独立于公网直连的安全边界需要补齐。** 公开服务应先提供配对授权、速率限制与消息校验，避免公开设备信息与任意信令转发。
- 计划不包含 TURN、WebSocket 文件中转、服务器上传存储或定时任务。
